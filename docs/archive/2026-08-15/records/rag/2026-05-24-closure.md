# RAG 阶段收口文档 - 2026-05-24

## 1. 收口结论

本阶段 RAG 优化可以收口。

收口含义不是“所有问题都彻底解决”，而是：

- 主链路能力已经补齐
- 默认回归入口已经收口
- 已验证失败的优化方向已经明确停止
- 下一步应先进入前后端联调，再决定后续优化

当前不建议继续在 RAG 单点上深挖。

## 2. 当前保留的主链路能力

当前主链路保留以下能力：

- Query Rewrite 受控接入
  - 规则优先
  - LLM rewrite 默认关闭
  - 失败自动回退
- 多路召回
  - 向量召回
  - 标题精确/contains/keyword/trigram/full-text
  - 内容侧 BM25
- 全通道 RRF 融合
- 当前已验证版本的 rerank 信号
  - lexical/title/content/path/structure
  - title BM25 signal
  - content BM25 signal
  - vector signal
- embedding 进程内 LRU 缓存
- 真实 KB 小样本回归入口

## 7. 明天联调建议关注点

前后端联调时，优先看这些问题，不要一开始就继续改 RAG：

- 检索接口是否稳定返回结果
- 标题类 query 是否能稳定命中
- 更像真实用户的自然问法是否能返回合理答案
- follow-up 场景是否至少能返回相关内容，而不是完全跑偏
- topic switch 后是否被旧上下文严重污染
- 响应耗时是否可接受
- 前端展示的引用/片段/排序结果是否符合预期

## 8. 联调后的决策规则

联调后再决定下一轮优化时，按这个顺序判断：

1. 如果主要问题是“接口不稳定 / 数据不通 / 展示不对”
   - 先修联调问题
   - 不动 RAG 策略
2. 如果主要问题是“候选明显相关，但首位不稳”
   - 再考虑 rerank 层
3. 如果主要问题是“压根没召回到”
   - 再考虑 recall / rewrite
4. 如果只是少量 follow-up case 不理想
   - 不做 case-by-case 补丁
   - 先累计联调现象再决定

## 9. 阶段性结论

当前最合理的动作不是继续优化 RAG，而是先联调。

这轮收口后，RAG 部分已经具备：

- 可运行
- 可回归
- 可解释
- 可继续观察

下一轮是否继续优化，应以联调现象为准，而不是继续离线深挖单点。
