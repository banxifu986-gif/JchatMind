## 1. 决策清单

| # | 决策 | 核心理由 | 代价 / 已知边界 | 细节页 |
| --- | --- | --- | --- | --- |
| 1 | **无状态 JWT + 每请求查库封禁**，不用 Redis 共享 Session | Redis 存的是鉴权旁路数据（验证码/限流），Redis 挂了只影响发码，已登录用户无感；无状态好横向扩展 | 每请求一次 DB 查询；无 refresh token、无登出黑名单——踢人靠封禁位 | [02](02-认证鉴权与异步邮件.md) §7 |
| 2 | **错误契约：HTTP 恒 200，语义走 `ApiResponse.code`** | 前端统一处理；`BizException` 必须带码（401/403）；内部异常细节不进响应体只进日志 | webhook 入站是例外（真实状态码）；调试时不能只看 HTTP 码 | [01](01-系统总览与运行边界.md) §7 |
| 3 | **单运行时 Agent，不引入多 Agent 编排** | RAG/记忆/MCP 都是 Agent 可调用能力；引入专职 Agent 须以冻结评测集上的质量/延迟/成本收益为依据 | 复杂任务靠显式工作流（未接普通聊天），无跨进程恢复 | [03](03-Agent核心循环.md) §8、[12](12-Skill与工作流.md) |
| 4 | **`internalToolExecutionEnabled=false`，应用显式编排 ReAct** | 审批、超时、审计、SSE 反馈全部经过应用层，不信任框架内隐式执行 | 代码复杂度高于 letting Spring AI 自执行 | [03](03-Agent核心循环.md) §1 |
| 5 | **fail-closed 哲学贯穿**：意图（模型兜底永不授予副作用）、记忆（模型输出不合法不写入）、迁移（状态未知拒绝）、检索（低置信拒答） | "高风险误调用优先为零"优于"分类 100% 正确"的宣称 | 拒答率上升是接受的代价 | [05](05-意图路由与工具选择.md)、[09](09-用户记忆.md)、[13](13-数据模型与迁移.md) |
| 6 | **手搓迁移框架保留，不换 Flyway**（2026-11-12 审查收口） | manifest+ledger+catalog 对账提供 SHA-256 级漂移防护与 fail-closed 基线契约；Flyway 的自动启动模式反而违背"迁移不随应用启动"要求 | 自维护成本；27 条迁移已验证 clean install + 对账 | [13](13-数据模型与迁移.md) §2 |
| 7 | **VectorChord-bm25 原生 BM25**，应用层只融合 rank/provenance | BM25 检索下推数据库，不再把整库文本拉回 JVM 打分；与 pgvector 同库 | 自建 PG 镜像（AGPL-3.0 or Elastic-2.0 双许可）；`similarity()` 函数形式不可索引 | [07](07-RAG摄入与索引.md) §6 |
| 8 | **任务队列至少一次语义，重复副作用不去重**（用户已接受） | advisory lock + RUNNING 可重认领换来崩溃恢复简单性；进程崩溃后自动续跑 | attempt_count 无上限、无退避；重复发信/重复工具副作用可能发生 | [04](04-异步任务调度.md) §3.3 |
| 9 | **意图规则优先，LLM 兜底默认关闭** | 规则可解释、可测、零成本；模型兜底需冻结 release 集校准后才可开启 | 语义边界 case（复合/澄清）靠 fail-closed 收窄 | [05](05-意图路由与工具选择.md) §4 |
| 10 | **评测门禁 fail-closed，default-switch 必须全子门过线** | 三路分支、rerank 开关等改动不能靠局部单测宣称完成 | 当前默认检索保持 R0；多层数据仍 candidate | [14](14-评测体系与门禁.md) §3 |
| 11 | **审批/熔断/审计用内存实现** | 单机演示校准；持久化是已记录的演进项，不是遗漏 | 重启丢审批与审计；多实例不同步 | [06](06-工具Harness.md) §1 |
| 12 | **防御等级按单机演示校准** | 不新增 write-only 审计、零调用协调层、为多实例准备的锁与队列 | 上生产前需重新评估每条边界 | [01](01-系统总览与运行边界.md) §7 |
| 13 | **前端 `rolldown-vite` 替换 Vite**（npm 别名 + overrides 强制） | 构建性能；API 兼容 Vite | 文档口径仍写"Vite" | [15](15-前端架构.md) §1 |
| 14 | **SSE 帧存 Redis（64 帧/30min）而非持久化事件流** | 覆盖断线重连与跨实例推送的最常见场景 | 不承诺分区/宿主机故障恢复；会话删除不清理 Redis key，靠 TTL | [10](10-SSE实时链路.md) §4/§7 |

## 2. 业界对比（摘要）

- **鉴权**：面向浏览器的单体/后台系统 Session（Spring Session + Redis）仍主流；前后端分离 + 多实例 JWT 更常见；生产主流是混合（短期 access JWT + refresh token 存 Redis + 黑名单）。纯无状态 JWT 几乎没有团队裸用。本项目是"无状态 JWT + DB 封禁检查"的折中；流量上来后一般换 Redis 用户缓存或本地短 TTL 缓存。
- **RAG 检索**：多路召回（dense + sparse + 资产通道）+ RRF 融合是当前主流实践；rerank（cross-encoder）默认关闭、按冻结 A/B 开启符合"先证明收益再切默认"的工程纪律。对 RAG-Anything 的借鉴限定为层级/位置保留与模态感知，未接 LightRAG 图谱。
- **任务调度**：PG advisory lock + durable queue 是小规模多实例的常见方案（省掉 MQ 依赖与去重复杂度）；规模上来后一般演进为 MQ + 幂等消费。
- **Agent 编排**：Function-calling ReAct + 20 步预算 + 显式 Harness 是当前 LangGraph/OpenAI Agents SDK 等框架的共同形态；项目未做的是持久化任务状态与跨进程恢复（复杂任务走显式 Planner→Verifier→Executor）。

## 3. 改决策前的检查清单

1. 这条决策是否来自某次审查收口（AGENTS.md"关键架构约定"节）？是 → 推翻需要明确理由并更新 AGENTS.md。
2. 是否影响评测可比性（RAG 通道/分块/排序）？是 → 必须走 [14](14-评测体系与门禁.md) 冻结集门禁。
3. 是否引入新依赖？全局规则要求先确认（无 Flyway/JPA/新状态管理方案是既定边界）。
4. 是否需要新能力边界（tenant、共享 ACL、多实例）？是 → 先扩展授权模型，不得把关系表投影误作授权模型。
5. 是否为"不可能出现的异常场景"写容错？项目纪律是不要——防御等级按单机演示校准。
