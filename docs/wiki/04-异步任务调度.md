# 异步任务调度

> 页面定位：用户消息从 HTTP 提交到 Agent 执行完成的异步链路——PG durable task queue、session advisory lock、worker 轮询与至少一次语义。改消息提交、执行队列、并发行为前必读。
>
> 最后核对：2026-11-14（按源码核验）。

## 1. 定位

Agent 执行不走 HTTP 请求线程：消息在一个 PostgreSQL 事务内持久化并写入 PENDING task，独立 worker 轮询认领后在有界线程池中执行。跨实例互斥靠 **PG session advisory lock**（锁 ID = `hashtextextended(sessionId, 0)`），进程崩溃后锁自动释放、RUNNING 任务可被重认领——**至少一次语义，重复副作用不做去重**（已接受的设计）。

## 3. 运行链路

### 3.1 提交 → 入队（同一 PostgreSQL 事务）

```text
POST /api/chat-messages（@NeedLogin）
→ ChatMessageFacadeServiceImpl.createChatMessage（@Transactional）
   ① reserveAgentTurnSequence —— INSERT ... ON CONFLICT (session_id) DO UPDATE
      SET next_sequence = next_sequence + 1 RETURNING next_sequence - 1（行级 UPSERT 原子取号）
   ② insert chat_message（USER）
   ③ insert agent_execution_turn_message
   ④ publishEvent(ChatEvent)
      → AgentExecutionTaskEnqueueListener.enqueue（Propagation.MANDATORY，无外层事务直接抛异常）
         写入 PENDING task（不含 prompt；userInput 仅内存瞬时传递，task 表无内容列）
→ 事务提交后响应 chatMessageId
```

写序契约由 `ChatMessageEventFlowIntegrationTest` 锁定：sequence → message → turn-link → event。

### 3.2 Worker 轮询 → 认领 → 执行 → 收束

1. `dispatchPendingTasks`（`fixedDelay=250ms`）：`isSaturated()`（active ≥ max）时跳过本轮；候选上限 `CLAIM_CANDIDATE_LIMIT=128`。
2. `findRunnableSessionHeads`：`status IN ('PENDING','RUNNING')` 且 `NOT EXISTS` 同 session 更小序号的 PENDING/RUNNING——**只取每 session 队首**，按 `created_at, id` 排序。
3. `sessionLockManager.tryLock(sessionId)`（非阻塞）：拿不到 → 跳过该 head，继续其余。
4. `claim`（独立短事务）：`UPDATE ... SET status='RUNNING', attempt_count=attempt_count+1, started_at=now, failure_type=NULL WHERE status IN ('PENDING','RUNNING') AND NOT EXISTS(更早未完成) RETURNING ...`——CAS 认领。
5. 提交 `agentExecutionWorkerExecutor`（**queue=0 不排队**）：池满 `TaskRejectedException` → `release` 回 PENDING（attempt_count-1）+ 计数，并**中断本轮后续派发**。
6. `execute`：`AgentExecutionTurnContext.run(sequenceNo, ...)` 包裹 `ChatEventListener.runPersistedTask` → `JChatMindFactory.create` + `JChatMind.run()`（见 [03](03-Agent核心循环.md)）→ SSE 推送（见 [10](10-SSE实时链路.md)）。
7. 收束：正常 → `complete`（RUNNING→COMPLETED）；Agent 异常 → `fail`（RUNNING→FAILED，`failure_type=异常类名`，无 message）；finally 中尝试候选记忆提取（失败只记类名不阻断），释放锁。

**注意**：claim 是独立事务，与持 advisory lock 的专用连接（`autoCommit=true`）不是同一连接；锁随连接存活，非事务锁。

### 3.3 崩溃恢复（至少一次）

进程崩溃 → PG 释放 session advisory lock → RUNNING 队首仍满足 `findRunnableSessionHeads`/`claim` 条件 → 其他 worker 重认领。`attempt_count` 仅递增、无上限校验（DB CHECK 仅 `attempt_count >= 0`），无重试退避——已产生的部分消息或工具副作用可能重复，用户已接受不做去重。

### 3.4 会话删除串行化

`deleteChatSession` → `ChatSessionExecutionCoordinator.execute`：进程内取票号顺序等待（`awaitTurn`）→ **阻塞式** `pg_advisory_lock`（与 worker 同一键空间互斥）→ 删除 → `ChatSessionDeletedEvent` → 记忆提取内存态清理。跨实例删除会等活动 turn 释放。

**测试专用路径**：`ChatEventListener.handle()` 直连路径（含 `agentTaskExecutor` 拒绝后重试一次）在生产代码中**无调用方**，仅测试使用；生产 durable 路径必经 worker。

## 4. 不变量与契约

1. `Propagation.MANDATORY`：入队必须运行在外层消息事务内（`AgentExecutionTaskEnqueueListener.java:22`）。
2. advisory lock 锁 ID：`hashtextextended(sessionId, 0)`；worker `pg_try_advisory_lock`（非阻塞）、删除协调 `pg_advisory_lock`（阻塞）；`SessionLock.close()` 为 synchronized，unlock 失败抛 `IllegalStateException`。
3. task 表不含 prompt：`ChatEvent.userInput` 仅提交事务内瞬时存在，worker 重建 ChatEvent 时传 null。
4. 队列 gate：`agent.execution.queue.enabled` 默认开启（`matchIfMissing=true`，yaml 无此键）；关闭时 worker 与 metrics 同时消失，主链路**无直连回退**、退化为不可用。
5. 队列操作全 `@Transactional` + `requireOne`（影响行数≠1 抛 `IllegalStateException`）。
6. 记忆提取失败隔离：只记 `e.getClass().getName()`（`MemoryExtractionFailureRegistry` 无异常 message/prompt）。
