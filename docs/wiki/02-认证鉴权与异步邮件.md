# 认证鉴权与异步邮件

> 页面定位：JWT 鉴权三层结构、邮箱验证码全链路（Redis 限流 + RabbitMQ 异步邮件）、Webhook 入站/出站。改登录/注册/验证码/权限/webhook 前必读。
>
> 最后核对：2026-11-14（按源码逐文件核验，含与架构文档的差异修正）。

## 1. 定位与鉴权三层

项目采用**无状态 JWT**，Redis 不参与登录态（只做验证码/限流旁路）。鉴权按三层收敛，后层只能收窄前层：

1. **网关放行**：`SecurityConfig` 对 `/api/**`、`/sse/**`、`/mcp`、`/mcp/**` 全部放行进 Spring MVC，其余路径 `anyRequest().authenticated()`；CSRF 关闭。**因此新增接口不得假设 SecurityFilterChain 已保护它**，必须显式使用下两层。
2. **切面校验**：`@NeedLogin`（方法级注解，仅 METHOD 目标）→ `NeedLoginAspect` 校验登录态并**每请求查库检查封禁**（`userMapper.findById`，`isBanned==1` → `BizException(403)`）。
3. **归属校验**：service 层以 `RequestScopeData.userId` 校验资源 owner。

事实修正：`NeedAdminAspect` 与 `@NeedAdmin` **在源码中不存在**（架构文档与根 README 的表述过时）；`isAdmin` 目前仅是 `User`/`LoginUserVO` 的字段。管理员能力路径出现前必须先建切面，不能只靠字段判断。

## 3. 请求鉴权链路

1. `TokenInterceptor.preHandle`：读 `Authorization`，`token.replace("Bearer ", "")` 后解析，写入 `RequestScopeData`。解析失败（含过期）静默置未登录，**不拦截请求**（`TokenInterceptor.java:23-44`）。
2. `NeedLoginAspect.around`：`@Around("@annotation(needLogin)")`；未登录 → `BizException(401)`；已登录查库，封禁 → `BizException(403, "账号已被封禁")`（`NeedLoginAspect.java:23-41`）。
3. service 归属校验：各 Facade 以当前用户过滤资源（如 `KnowledgeBaseAccessService` owner-only，见 [08](08-RAG检索与排序.md) §授权）。

`TokenInterceptor` 排除路径（`WebConfig`）：`/api/users/login`、`/api/users/register`、`/api/users`（精确匹配，不影响 `/api/users/whoami` 走拦截器）、`/api/email/verify-code`、`/api/webhooks/inbound/**`、`/health`、`/error`。CORS 仅 `http://localhost:*` / `http://127.0.0.1:*`（allowCredentials=true）。

**登录态事实**：`whoami` 每次调用签发新 token 并更新 `lastLoginAt`（隐式 token 轮换，`UserServiceImpl.java:118-140`）；无 refresh token、无登出黑名单——登出/踢人靠封禁位（每请求查库生效）。

## 4. 验证码与异步邮件

### 4.1 Redis key 全集（6 类，`RedisKey.java`）

| # | Key | TTL | 用途 |
| --- | --- | --- | --- |
| 1 | `email:{type}:verification_code:{email}` | 15min | 存验证码，验证成功即删 |
| 2 | `email:{type}:verification_code:limit:{email}` | 60s | 同邮箱发送频控 |
| 3 | `email:{type}:verification_code:limit:ip:{md5(ip)}` | 10min | IP 限流（≥20 拒绝） |
| 4 | `email:{type}:verification_code:rate_limit:{md5(email+ip)}` | 10min | 邮箱+IP 组合限流（≥5 拒绝） |
| 5 | `email:{type}:verification_code:error:{email}` | **5min** | 错码计数（≥5 后对码直接短路 false，**5 分钟窗口锁**，非永久） |
| 6 | `email:idempotent:{taskId}` | 1h | 消费者发送成功后写入，重投幂等 |

### 4.2 发码 → 发信 → 验证

- **发码** `POST /api/email/verify-code`（IP 取 `request.getRemoteAddr()`）：LOGIN 类型且邮箱未注册时 `shouldSend=false`——**限流标记照常写入但不发信**（防邮箱枚举，`EmailServiceImpl.java:96-113`）。正常路径构建 `EmailTask`（UUID、`expireAt=now+15min`）投递 RabbitMQ，并写冷却/计数 key。
- **发信** `EmailConsumer.onMessage`（MANUAL ack）：Redis 幂等命中 → ack 跳过；超 `expireAt` → DLQ；Thymeleaf 模板 `templates/mail/verify-code` 发信；成功后写验证码 key（**硬编码 15min，未复用 `mail.verify-code.expire-minutes` 配置**）+ 幂等 key；失败 `retryCount+1 < 3` 投 retry queue（`x-message-ttl=30s`，死信回主 exchange 实现 30s 延迟重试），否则写 `email_send_failure` 表。
- **死信** `EmailDeadLetterConsumer` 消费 `email.dlq` 落审计表（task_id/email/type/retry_count/failure_reason/trace_id/expired_flag）。
- **验证** `login`（verifyCode 模式）→ `checkVerificationCode`：error≥5 直接 false；对码成功删 code+error key；**错码同时递增 error、ip、rate 三个计数器**（`EmailServiceImpl.java:156-164`）。

**至少一次语义**：幂等 key 在发送成功后才写——"已发送但未写 key"时崩溃，重投会重复发信（已接受的边界）。

**覆盖缺口**：`EmailServiceImpl`/`EmailConsumer`/`EmailDeadLetterConsumer`/`UserServiceImpl`/`NeedLoginAspect` 无专属测试类。

**注册事实**：`register()` 只做账号/邮箱查重 + BCrypt，**不校验 REGISTER 验证码**；REGISTER 类型验证码仅有邮件主题定义，实际无人消费（`UserServiceImpl.java:34-66`）。

### 4.3 RabbitMQ 邮件拓扑

`email.exchange` / `email.queue` / `email.send` + `email.retry.exchange`/`email.retry.queue`（TTL 30s 回主队列）+ `email.dlx`/`email.dlq`；`EMAIL_MAX_RETRY_COUNT=3`。全库队列拓扑清单见 [13 数据模型与迁移](13-数据模型与迁移.md) §队列拓扑。

## 5. Webhook 入站与出站

**入站** `POST /api/webhooks/inbound/{sourceId}`（`InboundWebhookController`）：

1. 来源校验：未配置 → 404，配置非法 → 503；`WebhookProperties` 每来源必填 `ownerId`/`allowedKbIds`/`inboundSigningKey`/`callbackUrl`/`outboundSigningKey`，缺失在 `requireSource` 抛 IllegalStateException。
2. 限长：body 16384B（超 413）、eventId 256 字符、signature 128 字符。
3. 验签 `InboundWebhookVerifier`：HMAC-SHA256，签名帧为 BIG_ENDIAN length-prefixed `[schemaVer=1][len+sourceId][len+eventId][epochSec(8B)][len+payload]`（`WebhookSignature.sign`，出站入站共用，**不得自行实现**）；时间戳必须整秒且 `|偏移|≤5min`；`MessageDigest.isEqual` 恒时比较。失败映射：`DUPLICATE_EVENT`/`SOURCE_MISMATCH`/`INVALID_SIGNATURE`/`TIMESTAMP_OUT_OF_WINDOW` → 401，`INVALID_REQUEST` → 400。
4. payload 契约：JSON 对象**恰好**只有 `kbId`+`documentId` 两个文本字段；KB 白名单外 → 403。
5. 幂等与提交（`WebhookIngressService.submit`，`@Transactional`）：幂等键 `webhook:{eventHash}` 建摄入任务 + `webhook_inbox_event` 表 `UNIQUE(source_id, source_event_sha256)` 的 `ON CONFLICT` 对账（影响行数≠1 抛异常）；**Redis 事件预留放 afterCommit**（`jchatmind:webhook:{sha256(sourceId+eventId)}:event-id`，hash-tag 格式），避免"预留成功但事务回滚"。主幂等在 DB，Redis 只是旁路。成功 → 202 返回 `IngestionTaskVO`。

**注意**：webhook 入站是错误契约的例外——直接用真实 HTTP 状态码（404/413/400/401/403/422/202/503），不走 `ApiResponse` 恒 200 封套。

**出站** `WebhookDeliveryDispatcher`：`@Scheduled(fixedDelay=1000)` → `FOR UPDATE SKIP LOCKED` 租约领取 10 条 `PENDING/RETRYING` 且到期任务（领用即置 RETRYING、`next_attempt_at=now+30s`）；payload SHA-256 校验后用 `outboundSigningKey` 签名 POST 回调（头 `X-Webhook-Event-Id/Timestamp/Signature`，请求超时 5s、连接 3s、禁止重定向）；2xx → DELIVERED；失败按 `1,2,4,8,16,32→60min` 封顶退避，`max_attempts`（默认 5，DB 约束 1..10）耗尽 → DEAD_LETTER。事件类型仅三种：`INGESTION_SUCCEEDED`/`INGESTION_FAILED`/`APPROVAL_PENDING`（代码 Set 与 DB CHECK 双重约束）。审批事件由 `WebhookApprovalOutboxService.enqueue` 生成（校验 `ownerId==source.ownerId`，`ON CONFLICT DO NOTHING`）。

## 6. 不变量与契约

- JWT：HS512、claims 仅 `userId`、默认 30 天（`jwt.expiration=2592000`）；无 refresh、无黑名单。
- 封禁生效路径：每请求查库（`NeedLoginAspect.java:31-39`）——Redis 挂了不影响已登录用户，只影响发码/防刷。
- 密码 BCrypt；`jchatmind_user` 表 account(32)/username(16) UNIQUE、`is_banned`/`is_admin` SMALLINT NOT NULL DEFAULT 0。
- 错误契约：鉴权失败抛 `BizException(401/403)`，HTTP 恒 200；仅 webhook 入站例外（见 §5）。
- 事务边界：webhook ingress 的验签/幂等对账在事务内，Redis 预留在 afterCommit——与"事务内不做磁盘 IO/外部副作用"的全局约定一致。

## 7. 设计取舍：无状态 JWT vs Redis 共享 Session

关键差异在 **Redis 里存什么**：

| | 共享 Session（Spring Session + Redis） | 本项目（无状态 JWT + 每请求查库封禁） |
| --- | --- | --- |
| Redis 存什么 | **登录态本身**（sessionId → user） | **鉴权流程辅助数据**（一次性 code、计数器） |
| Redis 的角色 | 鉴权必经之路，挂了全员掉线 | 旁路，挂了只影响发码/防刷，已登录用户无感 |
| 登出/踢人 | 即时（删 session） | 靠封禁位每请求查库生效 |
| 扩展性 | session 黏性或共享存储 | 天然无状态，好横向扩展 |

业界现状：面向浏览器的单体/后台系统 Session 仍主流；前后端分离 + 多实例场景 JWT 更常见；**生产主流其实是混合**——短期 access token (JWT) + refresh token 存 Redis + 登出/封禁走 Redis 黑名单（"有状态的 JWT"）。纯无状态 JWT 几乎没有团队裸用（无法即时踢人）。本项目用"每请求一次 DB 查询"换封禁可控性，省掉黑名单——对小项目是合理折中；流量上来后一般会换成 Redis 用户缓存或本地短 TTL 缓存。
