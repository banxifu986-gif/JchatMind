# 数据模型与迁移

> 页面定位：PostgreSQL 表清单、手搓迁移框架的 fail-closed 契约、RabbitMQ 队列拓扑、运行配置与依赖。动 schema、加迁移、改配置前必读。
>
> 最后核对：2026-11-14（按源码与 manifest 核验）。

## 1. 定位

持久化只有 **MyBatis + JdbcTemplate**（无 JPA、无 Flyway/Liquibase）。schema 变更走自研迁移框架：`sql/migrations/manifest.json` 是唯一顺序来源，每条迁移带 SHA-256，执行走 ledger 表 + advisory lock + catalog 对账，**不随应用启动运行**。模型服务（DeepSeek/GLM）由 Spring AI 装配，bean 名即模型 key。

### 2.1 manifest（`sql/migrations/manifest.json`）

- 当前 **27 条迁移**，order 10→270 步长 10；`manifestVersion=1`、`schemaVersion=2026-10-22-g9`。（事实修正：架构文档头部"迁移 manifest 24 项"与 5.1 节"验证 25 条"为 order 250/260/270 加入前的旧数字。）
- 全部 `transactional=true`，唯一例外 order 80 `user-memory.create-cosine-index`（`false`，ivfflat 并发建索引）。
- 依赖链 `requires`：引用 `baseline.*`（application-schema / user-memory / user-memory-candidate / chunk-bge-m3 / knowledge-base / document / agent）、`manual.*`（当前仅 order 110 的 `manual.owner-review`，须 `--approve` 显式批准）与先行迁移。
- 路径解析禁止逃逸 project root（`resolveProjectPath`）。

### 2.2 fail-closed 三层

1. manifest 必须声明 `baseline.required=true` + `failClosedOnUnknownState=true`；order 严格递增、id/path 唯一、sha256 小写 64 hex 且与实际文件一致。
2. 无 ledger 但库中已有用户对象 → unknown state 拒绝；ledger 与 manifest 任何不对齐（缺/重/乱序/hash 不符/RUNNING 残留/未知 status）→ 拒绝。
3. SQL 执行前二次 SHA-256 校验（`readVerifiedSql`）。

**ledger**：`public.jchatmind_schema_migration_ledger`（`migration_id PK / order / sha256 / status CHECK IN('RUNNING','APPLIED') / started_at / completed_at`）；基线行 `__baseline__` order=0；时间戳一致性校验（APPLIED 必有 completed、RUNNING 必无）。迁移锁 `pg_try_advisory_lock(hashtextextended('jchatmind.schema.migration', 0))`，等待 30s、25ms 轮询。

### 2.3 发布入口与对账

- 只走 `MigrationReleaseApplication` main（`--confirm-schema-release`；密码仅从 `--password-env` 读）；命令模板见 [sql/migrations/README.md](../../sql/migrations/README.md)。**代码中无任何启动钩子调用 `migrate()`**——把迁移绑定到普通应用启动是被禁止的。
- 迁移后在同一 advisory lock 下用 `REPEATABLE_READ` 快照对账 catalog：`catalog-contract.json` 声明 `requiredExtensions=[vector, vchord_bm25, pg_trgm]`、36 张 requiredTables、`forbiddenColumns` 唯一条目 `agent.allowed_kbs`（证明 `allowedKbs` 只是 `agent_knowledge_base` 关系表的投影，不是物理列）；定义比对支持 `exact` 与 `contains:` 两种匹配。
- 发布报告写 `target/migration-release/release.json`（三方 SHA/批准项/release-id/code-revision/rollback 固定 `manual_restore_and_rebuild_required`），不记录 JDBC 地址/用户名/密码/SQL 正文。

### 3.1 SQL 调优基线（2026-11-12 收口）

- **索引**：order 250 `sql/knowledge-base/2026-11-12-add-hot-filter-indexes.sql` 新增 5 个 B-tree——`chunk_bge_m3(doc_id)`、`chunk_bge_m3(kb_id)`、`chat_message(session_id)`、`chat_session(user_id)`、`user_memory(user_id)`；manifest 与 catalog-contract（含 contract SHA）已同步。**新增/修改索引必须沿用迁移流程，禁止手工 `CREATE INDEX` 掩盖漂移。**
- **order 260 标题检索索引**：`idx_chunk_bge_m3_title_trgm` / `idx_chunk_bge_m3_content_path_trgm`（GIN trgm，表达式与 mapper 谓词逐字符一致；`pg_trgm` 由迁移安装并进契约 `requiredExtensions`）。单 KB chunk 上千且有选择性模式时 6–10× 收益；`similarity()` 函数形式不可索引（需 `%` 操作符 + GUC 阈值，涉语义变更，未做）。
- **查询模式**：删除文档/重传用单条 `DELETE FROM chunk_bge_m3 WHERE doc_id`（`deleteByDocId`）；KB 归属校验复用 `KnowledgeBaseMapper.selectByIdBatch`；`getDocuments` 走 `selectByKbIds`、`getAgents` 走 `selectKbIdsByAgentIds` 批量绑定；记忆冲突查重走 `selectActiveByUserIdAndMemoryType`（LIMIT 1）。循环内逐条查询/删除的写法不再新增。
- **RAG 候选边界**：`selectTitlePathCandidatesByKbIds` 固定 `ORDER BY created_at, id LIMIT 500`，超大 KB 的 auto-context 候选按最旧优先截断。
- **记忆链路口径**：列表/提取/召回 fallback 不携带 embedding（专属 `BaseResultMapNoEmbedding`）；语义查重走 `existsActiveSemanticDuplicate`（SQL `EXISTS` + `<=>` 距离阈值精确逐行计算，不走 ivfflat 以避免近似漏判）；无向量记忆补充走 `selectActiveWithoutEmbeddingByUserId`。不要新增全量加载记忆后 Java 侧算余弦的路径。
- **dev 库收编**：本机 `jchatmind` 库已于 2026-11-12 完成 Flyway-baseline 式收编（清理遗留漂移 → 台账补种 → 发布入口 upgrade 应用 240/250 → catalog 对账 SUCCEEDED，台账 26 行全 APPLIED）；此后 dev 库 schema 变更必须走迁移框架。契约 `allowedConstraints` 现容纳 4 个原始 schema 外键（`chat_session_agent_id_fkey`、`chunk_bge_m3_kb_id_fkey`、`user_memory_session_id_fkey`、`user_memory_candidate_session_id_fkey`）。
- 调优前后性能对比（p50/p95/p99）与测量脚本见[归档报告](../archive/2026-11-12/sql-tuning/REPORT.md)。

## 4. RabbitMQ 队列拓扑全清单（`config/RabbitMQConfig.java`）

四组业务队列，同构拓扑：durable 主队列（DLX 指向各自 DLX）+ TTL 重试队列（`x-message-ttl=30s` 死信回主 exchange 原 routing key）+ durable DLQ，全部 DirectExchange：

| 业务 | exchange / queue / routing | 最大重试 | 消费者 / prefetch |
| --- | --- | --- | --- |
| email | `email.exchange` / `email.queue` / `email.send` | 3 | 默认 factory（yaml manual ack） |
| ingestion | `ingestion.exchange` / `ingestion.queue` / `ingestion.submit` | 3 | 2 / 1（专属 factory，**显式 AUTO ack**，覆盖 yaml manual） |
| knowledge-base-deletion | `knowledge-base-deletion.exchange` / `.queue` / `knowledge-base-deletion.submit` | 无 MAX_RETRY_COUNT 常量 | 1 / 1 |
| builtin-skill-task | `builtin-skill-task.exchange` / `.queue` / `builtin-skill-task.execute`；DLQ routing key `builtin-skill-task.dead-letter`（**四组中唯一命名不同**） | 无常量（代码取 5） | 2 / 1 |

`rabbitTemplate`：Jackson2JsonMessageConverter + JavaTimeModule；publisher confirm 空操作（重试由 DLX 拓扑承担）。任务 ID 以 JSON 字符串投递，消费者入口须剥引号再查 UUID。
