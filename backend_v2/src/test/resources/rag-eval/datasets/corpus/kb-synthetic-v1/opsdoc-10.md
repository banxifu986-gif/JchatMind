# DNS 记录管理手册

本文档为企业内部知识库文档，供员工与系统检索使用。

## 附录：检查清单

本附录用于 DNS 记录变更的执行前核对与执行后确认。所有检查项均需在星澜工作台变更单中逐项勾选并留存记录；未通过执行前核对的变更不得进入实施环节。

**一、执行前核对项**

- [ ] 变更单已关联明确的域名、记录类型、记录值、TTL 与生效范围，且与星澜云控制台中现有配置一致。
- [ ] 变更原因、影响面与回滚方案已填写完整，回滚方案包含原记录值快照与预计回滚耗时。
- [ ] 审批已闭环：标准变更的审批流程标准时效为 2 个工作日，加急为 4 小时；超出时效未获批准的变更须重新提交，不得先行实施。
- [ ] 已确认变更不涉及核心服务的解析入口，或已就核心服务可用性 SLA 为 99.95% 的影响评估取得业务负责人书面确认。
- [ ] 变更窗口已避开的业务高峰与既定发布冻结期，值班人员已知悉窗口时间。
- [ ] TTL 已按变更类型调整：计划内切换建议提前下调 TTL 并等待旧 TTL 过期后再执行。
- [ ] 监控与拨测项已覆盖待变更域名，告警通知对象已确认为当班值班人。
- [ ] 双人复核已完成：执行人与复核人不得为同一人，复核人须具备 DNS 变更权限。

**二、执行后核对项**

- [ ] 变更结果已与变更单逐字段比对，记录值、TTL、记录类型无偏差。
- [ ] 权威 DNS 与递归解析结果已在至少两个外部网络位置验证一致。
- [ ] 相关业务域名访问正常，核心服务可用性 SLA 为 99.95% 的监控指标未出现异常波动。
- [ ] 监控与拨测在变更后观察期内无新增告警，观察期时长按变更单约定执行。
- [ ] 变更单已回填实际执行时间、执行人、验证结论与截图证据。
- [ ] 若触发回滚，已按回滚方案恢复原记录值并复验，且在变更单中记录回滚原因。
- [ ] 配置快照与变更记录已归档至星澜工作台知识库，供后续审计追溯。

**三、异常处理**

任一核对项未通过时，执行人须立即暂停后续操作，在星澜工作台变更单中标注未通过项与初步判断，并通知值班负责人；涉及核心服务解析的场景按应急预案升级处理，不得以口头确认替代书面记录。

## 审核时效

本节的审核时效规则适用于所有通过星澜云控制台提交、并经星澜工作台审批流转的 DNS 记录变更工单，包括新增、修改、删除与委托解析调整。任何记录在审批通过前不得下发至解析节点。

**操作审批时效**

- 审批流程标准时效为 2 个工作日，加急为 4 小时。时效自工单在星澜工作台流转至当前审批人之时起算，按公司工作日历计算。
- 审批人对工单的每一次退回，都必须在退回意见中写明缺失材料或需要澄清的问题；工单处于退回待补充状态期间不计入审批时效，申请人补齐材料并重新提交后，时效重新起算。
- 申请人发起加急时，须在工单中说明加急理由、受影响的业务范围与期望生效时间，并经值班负责人确认后方可进入加急通道。加急通道仅用于有明确时间窗口的变更，不得用于规避正常审批。
- 核心服务可用性 SLA 为 99.95%，审批排队不得成为影响该目标的延误原因。对涉及核心服务域名的工单，审批人应优先处理；预计无法在标准时效内完成的，应主动在工单中说明原因并指定代审批人。
- 工单超出对应时效仍未处理时，系统自动升级提醒至审批人的上级；申请人可在工单内追加备注说明影响，但不得自行跳过审批直接下发记录。

**应急免审批条件**

仅当同时满足“故障正在发生”与“变更属于最小必要范围”两项前提时，方可先执行变更、后补审批，具体情形包括：

- 核心服务或对外域名的解析结果异常，已造成业务不可用或大范围访问失败；
- 发生域名劫持、未授权记录写入等安全事件，需要立即恢复或隔离；
- 上游解析服务商故障，需要紧急切换解析线路以恢复服务。

执行要求：操作人应为当班值班人员；操作前须在星澜工作台创建工单草稿，记录变更内容、影响范围与判断依据；操作后立即通知审批人与业务负责人；服务恢复后第一时间补齐审批流程，并在工单中标注为应急变更。免审批不得顺带调整与故障无关的记录，应急操作与补审批记录均须纳入审计留痕，作为后续复盘的依据。

## 适用场景

本手册适用于星澜科技内部所有涉及 DNS 记录新增、变更、删除与核查的操作场景，涵盖星澜工作台、星澜云控制台及其对外发布的域名解析配置。凡在下列任一触发条件下开展操作，均须先完成本节规定的前置检查，评估影响范围后再进入后续流程。

**一、触发条件**

出现以下任一情形时，即触发本手册流程：

1. 新增子域名或主机记录，用于新服务上线、测试环境搭建、活动页面发布；
2. 变更现有 A、AAAA、CNAME、MX、TXT、NS 等记录指向，包括切换 IP、调整负载均衡后端、迁移 CDN 服务商；
3. 删除不再使用的记录，或对记录进行批量清理；
4. 域名注册商、权威 DNS 服务商发生变更，或 NS 记录调整；
5. 证书签发、域名归属验证等需要临时添加 TXT 记录的场景；
6. 解析异常排查中需要临时调整记录以定位问题。

**二、影响范围**

DNS 记录变更直接影响用户对星澜工作台与星澜云控制台的访问可达性，需按以下维度评估：

1. 业务范围：区分核心服务与非核心服务。核心服务可用性 SLA 为 99.95%，任何涉及核心服务域名的记录变更均视为高风险操作，须安排在与业务低峰期一致的窗口执行；
2. 用户范围：评估受影响的租户数量、地域分布及是否存在正在进行的重大客户交付；
3. 生效范围：明确记录的 TTL 设置，判断变更在全球递归解析器中的缓存扩散时间，避免出现新旧记录并存的过渡期不一致；
4. 关联范围：确认该域名是否被证书、回调地址、白名单、邮件域 SPF/DKIM 配置引用，避免单点变更引发连锁故障。

**三、前置检查**

操作前须逐项完成并留痕：

1. 核对记录现状：通过权威 DNS 服务商与公共解析工具双重确认当前记录值、TTL 及解析生效状态；
2. 确认变更必要性与准确性：由需求提出方书面说明目标记录类型、主机记录、记录值及生效时间；
3. 完成审批：标准变更按审批流程标准时效为 2 个工作日执行，加急变更按加急时效为 4 小时执行，未取得审批不得操作；
4. 制定回滚方案：保留变更前记录快照，明确回滚触发条件与责任人；
5. 准备验证手段：约定变更后的解析验证方式与观测时长，确保在星澜工作台工单中可追溯。

上述检查未全部通过的，不得进入实际配置阶段。

## 回滚方案

**回滚触发条件**

DNS 记录变更发布后，出现下列任一情形即判定为需要回滚，不再继续观察：

- 核心服务可用性出现下降趋势，监测数值低于核心服务可用性 SLA 为 99.95% 的承诺水平；
- 星澜工作台或星澜云控制台出现成片解析失败，智能客服与数据分析服务无法正常访问；
- 权威解析与递归解析结果持续不一致，且无法在可控时间内定位原因；
- 变更内容本身有误，包括域名、记录类型、TTL 或目标值填写错误；
- 变更引发了非预期的流量切换，或导致第三方校验失败。

**回滚步骤**

1. 值班工程师在星澜工作台提交 DNS 回滚工单，注明触发条件、影响范围与受影响的业务系统。审批流程标准时效为 2 个工作日，加急为 4 小时；回滚一律按加急提交并说明原因。
2. 从变更前的记录快照恢复，逐条核对域名、记录类型、TTL 与目标值，确保与原值完全一致，不在回滚过程中附带其他调整。
3. 在星澜云控制台按“先恢复权威记录、后刷新缓存”的顺序执行恢复，TTL 沿用变更前的取值。
4. 执行双人复核，操作人与复核人分别确认记录差异为空后，方可提交生效。
5. 在工单中记录回滚开始时间、生效时间、操作人与复核人，以及回滚前后的记录差异。

**回滚后验证**

- 通过多地解析探测确认记录已返回变更前的值，解析链路无异常。
- 持续观察核心服务可用性，确认稳定回到核心服务可用性 SLA 为 99.95% 之上的水平。
- 核对星澜工作台告警与业务监控，确认错误率、响应时间恢复至变更前基线。
- 保留回滚快照与工单记录，供后续复盘使用；复盘结论需回填至原变更单。
