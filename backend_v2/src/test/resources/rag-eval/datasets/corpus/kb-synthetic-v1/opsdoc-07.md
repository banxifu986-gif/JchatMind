# 监控告警配置手册

本文档为企业内部知识库文档，供员工与系统检索使用。

## 责任分工

监控告警的责任分工在告警产生时即刻生效，遵循"一事一指挥、一事一执行、一事一通报"的原则。告警触发后，值班负责人须在告警确认环节同时锁定指挥者、执行者与通报对象三类角色，并在星澜工作台的告警工单中记录，避免出现无人决策或重复处置。

**指挥者**

指挥者由当班值班负责人担任，是单条告警或单个故障事件的唯一决策人。其职责包括：确认告警等级与影响范围，决定是否升级为故障事件；分配执行者并明确处置时限；判断是否需要暂停相关变更、降级或限流；决定对外通报的时机与口径；在事件结束后组织复盘并在工单中关闭。同一事件在任一时刻只允许存在一名指挥者，交接班或升级时必须显式移交并在工单中写明移交时间与接手人。指挥者不直接操作生产环境，以避免决策与执行相互干扰。

**执行者**

执行者由当班运维工程师担任，必要时由对应业务线的研发值班人员协同。执行者负责按指挥者下达的指令实施排查与恢复，逐条回填处置动作与时间点，并在操作前评估影响范围与回滚方案。涉及生产服务器登录排查时，须通过堡垒机进行，堡垒机会话默认录屏审计保留 180 天，执行者应在工单中登记会话编号与时间段，便于事后回溯与复盘取证。告警涉及星澜云控制台侧的 API 网关时，执行者应先确认 API 网关默认限流为每客户端 200 QPS，据此区分是正常容量触顶、突发流量还是调用方异常重试，再向指挥者提出扩容、限流调整或流量封禁的建议，不得自行变更限流配置。

**通报对象**

通报对象按事件影响面确定，包括受影响的业务线负责人、相关研发与客服支撑团队，以及需要知情的管理层；涉及用户数据或账号安全的事件，还须同步安全与合规团队。通报内容统一包含：事件现象、影响范围、当前处置进展、下一次更新时间。指挥者负责确认通报对象名单与通报频次，执行者负责提供事实性数据，禁止在通报中使用未经确认的原因判断或完成时间承诺。通报记录与告警工单一并归档，作为复盘与责任界定的依据。

## 操作步骤

本 section 的全部操作在星澜工作台内完成；当告警指标来自云上资源时，需先在星澜工作台完成规则登记，再跳转至星澜云控制台核对指标口径。以下步骤按顺序执行，每步完成后再进入下一步。

1. 登录星澜工作台并进入监控告警模块。使用企业账号登录星澜工作台，在左侧导航依次选择「监控告警」→「告警规则」。
   验证点：页面右上角显示当前账号所属组织与角色；规则列表正常加载且无报错提示。
   【截图占位：告警规则列表页，标注右上角组织信息与「新建规则」按钮】

2. 新建告警规则。点击「新建规则」，填写规则名称、监控对象、监控指标、阈值与持续周期；阈值与持续周期按业务实际填写，本手册不预设具体取值。
   验证点：保存后规则出现在列表中，状态为「已启用」，并生成唯一规则 ID。
   命令示例占位：`xlctl alert rule create --name <规则名> --metric <指标> --threshold <阈值> --for <持续周期>`

3. 绑定通知渠道与接收人。选择已开通的通知渠道，指定接收组与升级策略，并确认通知时段。
   验证点：点击「发送测试通知」后，接收组内成员收到消息，通知记录中生成一条发送成功条目。
   【截图占位：通知配置页与测试通知成功提示】

4. 配置资源范围与静默策略。按标签或资源清单圈定生效范围，并为计划内变更设置静默窗口。
   验证点：范围预览显示的资源数量与预期一致；静默窗口在规则详情中可见且起止时间正确。

5. 触发一次验证告警。通过测试告警入口或将阈值临时调整后触发，确认链路完整后再恢复原配置。
   验证点：告警事件出现在「告警事件」列表，接收人收到通知，事件状态可由「触发中」流转至「已恢复」。

6. 确认审计留存。告警规则属于配置变更，经堡垒机执行的变更会话会录屏归档；堡垒机会话默认录屏审计保留 180 天，请在审计查询页面确认本次会话记录可检索、可回放。
   验证点：审计查询结果中包含本次会话记录，且保留期字段显示为 180 天。
   【截图占位：堡垒机审计查询结果页，标注会话时间与保留期】

7. 配置 API 网关限流相关告警。在星澜云控制台的 API 网关监控项中，为关键客户端建立限流触发类告警。API 网关默认限流为每客户端 200 QPS，配置阈值时以此为基线进行比对，避免阈值高于默认限流值而长期不触发。
   验证点：规则详情中可见基线说明；保存后监控图表能正常展示该客户端的 QPS 曲线。
   命令示例占位：`xlctl gateway quota describe --client <客户端标识>`

8. 归档与交接。将本次新增规则的名称、ID、接收组与验证结果登记到运维记录，并通知值班同学。
   验证点：运维记录中可检索到规则 ID，且值班交接内容与规则列表一致。

## 责任分工

责任分工按“谁配置、谁确认、谁复核”三层划分，确保每条告警都有明确归属，避免告警无人处理或重复处理。

- 告警配置责任人：由各业务线指定的运维负责人担任，负责在星澜云控制台完成告警规则的新增、修改与停用，并在星澜工作台登记变更说明。
- 告警复核人：由平台运维组值班人员担任，负责审核规则的阈值、通知渠道与升级路径是否合理，审核通过后方可生效。
- 业务确认人：由对应业务负责人担任，负责确认告警所覆盖的服务范围与影响范围，避免将非本业务线的实例纳入规则。

触发条件

出现以下任一情形时，责任分工自动进入升级流程：告警规则需要调整影响范围；同一告警在 24 小时内重复触发且未定位原因；告警通知对象发生人员变动；涉及安全审计类告警的配置变更。升级后由平台运维组牵头，业务确认人配合，必要时通知安全合规组参与。

影响范围

配置前必须写明影响范围，包括涉及的实例、环境与通知对象。影响范围涉及生产环境时，须由业务确认人书面确认；涉及审计追溯的，须确认堡垒机会话默认录屏审计保留 180 天，确保变更过程可回溯；涉及接口类告警的，须确认 API 网关默认限流为每客户端 200 QPS，避免因误调阈值掩盖真实的限流问题。

前置检查

1. 确认配置人具备星澜云控制台对应项目的告警管理权限。
2. 确认告警规则已关联正确的业务标签与值班组。
3. 确认通知渠道可用，且接收人已知悉该告警的含义。
4. 确认本次变更不影响既有审计与限流策略，相关记录已在星澜工作台留档。

完成上述检查后，配置人提交规则，复核人审核，业务确认人确认影响范围，三方职责闭环后方可发布。

## 回滚方案

本方案适用于星澜工作台监控告警配置变更（含告警规则、阈值、通知策略、静默规则及告警通道配置）在发布后出现异常时的回滚操作。所有回滚操作须通过星澜工作台运维通道执行，操作过程纳入堡垒机会话录屏审计，堡垒机会话默认录屏审计保留 180 天，回滚全过程可追溯。

**一、回滚触发条件**

满足下列任一条件即应启动回滚，由值班运维提出、当班负责人确认后执行：

1. 变更发布后 30 分钟内，核心业务告警出现明显漏报，经确认为本次配置变更引入；
2. 告警误报量在发布后显著上升，造成通知通道拥塞或值班人员无法有效处置；
3. 告警规则求值异常，规则持续报错或求值超时，导致监控覆盖出现缺口；
4. 配置变更引发星澜云控制台相关接口调用异常，异常调用量导致 API 网关触发限流保护；需注意 API 网关默认限流为每客户端 200 QPS，变更评估时不得使单客户端调用峰值逼近该上限；
5. 变更内容与评审记录不一致，或缺少必要审批留痕。

**二、回滚步骤**

1. 冻结变更：在星澜工作台将本次变更批次标记为“回滚中”，暂停后续发布队列，禁止他人在同一配置项上并行修改。
2. 确认基线：从配置版本库取出变更前的最后一个已评审版本号，核对版本号、变更单号与生效环境一致。
3. 执行回滚：在星澜工作台告警配置模块选择目标基线版本执行回滚发布；如涉及告警通道参数，同步在星澜云控制台恢复对应通道配置。操作前开启堡垒机会话录屏。
4. 逐项核对：回滚完成后按变更清单逐条比对告警规则、阈值、通知策略与静默规则，确认与基线一致，无残留新增规则。
5. 记录留痕：在变更单中填写回滚原因、回滚版本号、执行人与执行时间，并关联堡垒机会话记录编号，便于在审计保留期内追溯。

**三、回滚后验证**

1. 规则有效性：确认全部告警规则处于正常求值状态，无报错、无超时，规则数量与基线一致。
2. 通知链路：使用测试告警分别验证邮件、短信与工作台通知通道可达，通知内容与接收人范围符合基线配置。
3. 业务观测：观察核心业务指标 30 分钟以上，确认漏报与误报回到变更前水平；观察 API 网关各客户端调用量，确认无客户端接近每客户端 200 QPS 的默认限流阈值。
4. 静默与抑制：核查临时静默规则已按基线清理，避免掩盖真实告警。
5. 复盘归档：验证通过后由值班负责人在变更单中确认回滚完成，并在 1 个工作日内输出简要复盘，明确后续修复方案与重新发布的时间窗口。
