# JChatMind Agent 执行与记忆边界

> 语料属性：`synthetic/project-grounded`
>
> 用途：RAG Phase B 的新增候选语料，用于构造 Agent 编排、工具调用安全、失败恢复和记忆系统边界的评测样本。
>
> 状态：候选语料，不属于冻结的 `fixture-fast-v1` 或 `regression-v1`，不得直接作为发布集或运行时事实来源。
>
> 编写依据：项目的 Agent Harness 已完成方案与记忆系统改进方案。Harness 内容描述已实现行为；记忆优化内容只描述现状问题和规划，不能表述为已经上线。

## 1. Agent 执行主链路

一次聊天请求从 `ChatMessageController` 进入，经由消息门面、事件发布和事件监听后，由 `JChatMindFactory` 创建 Agent 并调用 `JChatMind.run()`。

Agent 的单轮执行按 `think()` 和 `execute()` 两个阶段推进：

1. `think()` 负责让模型决定是否发起工具调用。
2. `execute()` 在真正执行工具前执行 Harness 的 pre-flight 检查。
3. 允许执行的调用交给 `ToolCallingManager.executeToolCalls(...)`。
4. 被拒绝、超时或熔断的调用不执行真实工具，而是返回 synthetic tool response。
5. 真实结果与 synthetic 结果合并后回到 Agent 对话链路。

Harness 不是模型可选择的普通 Tool。它位于工具执行的外围，用于统一约束本地与外部 `ToolCallback`，因此模型不能通过“不选择 Harness”绕过审批、熔断或审计。

## 2. 为什么需要两层工具保护

工具调用保护有两个接入点，职责不同：

- `JChatMindFactory` 统一包装本地工具和外部 `ToolCallbackProvider` 提供的工具，保证来源不同的工具都经过同一套保护。
- `JChatMind.execute()` 在调用工具管理器之前进行 pre-flight，集中处理待审批、熔断和结果合并。

只在 callback 层做代理不足以处理审批等待和整批 tool call 的拆分；只在 Agent 主链路做判断又可能遗漏外部工具。两层组合的目标是“统一覆盖”，不是重复执行业务工具。

## 3. 人工审批

人工审批用于高风险工具。命中审批配置的工具在执行前创建 `ApprovalRequest` 并向客户端发送 `TOOL_APPROVAL_REQUIRED` 事件。

审批有四种状态：

- `PENDING`：等待用户决定。
- `APPROVED`：允许执行。
- `REJECTED`：用户明确拒绝，不执行工具。
- `EXPIRED`：在超时时间内未决定，不执行工具。

同一 step 内相同 `toolName` 的多次调用会聚合为一个审批请求；用户批准后，该 step 内同名调用一并放行。拒绝和超时分别返回以下 synthetic tool response：

```text
[APPROVAL_REJECTED] 工具 {name} 执行被用户拒绝
[APPROVAL_EXPIRED] 工具 {name} 审批超时，未执行
```

审批拒绝或超时代表用户或流程决策，不代表工具本身发生故障，因此不应计入熔断器失败次数。

## 4. 熔断与失败恢复

熔断器仅对配置中指定的工具生效，并维护 `CLOSED`、`OPEN` 和 `HALF_OPEN` 三种状态：

1. `CLOSED` 状态下，连续执行失败达到阈值后切换到 `OPEN`。
2. `OPEN` 状态下，工具暂不执行，直接返回不可用结果。
3. 恢复时间到达后进入 `HALF_OPEN`，允许一次试探调用。
4. 试探成功回到 `CLOSED`；试探失败重新回到 `OPEN`。

熔断时返回：

```text
[CIRCUIT_BREAKER_OPEN] 工具 {name} 暂时不可用，请稍后重试
```

熔断保护的是持续失败造成的级联影响，不负责判断模型回答是否真实，也不能替代权限校验或输入校验。

## 5. 审计与可观测性

每次工具调用需要形成结构化 `ToolCallRecord`。记录至少包含会话、Agent、工具调用标识、工具名、输入、结果、成功状态、失败信息、耗时、时间戳和 step 编号。

审计 outcome 应区分以下结局：

- `SUCCESS`：工具真实执行成功。
- `ERROR`：工具真实执行失败。
- `REJECTED`：用户拒绝审批。
- `EXPIRED`：审批超时。
- `CIRCUIT_OPEN`：工具被熔断器阻断。

当前 MVP 的审批、熔断和审计存储均为单机内存实现。它适合本地单实例验证，但进程重启后状态不保证恢复，也不保证多实例一致性。需要跨重启或多实例部署时，应改用持久化或共享状态存储。

## 6. SSE 状态语义

Agent 执行过程中可以向前端推送状态事件：

- `AI_PLANNING`：开始规划。
- `AI_THINKING`：模型进行下一轮推理。
- `AI_EXECUTING`：即将执行工具。
- `TOOL_APPROVAL_REQUIRED`：存在待审批工具调用。
- `AI_DONE`：对话完成或异常结束。

审批事件携带审批请求标识、工具名、工具输入、聚合调用数量、过期时间和 step 编号。前端若未实现审批卡片，也不能把没有批准的调用视为已经执行。

## 7. 用户记忆的当前边界

用户记忆改进方案仍处于设计阶段。下面列出的是当前已识别的问题和计划方向，不是已完成能力：

- 当前对话摘要可能采用旧摘要与新摘要持续累加的方式，长对话下会无限膨胀。
- 当前阈值以字符数近似上下文大小，不能准确反映中文、英文和代码的 token 差异。
- 记忆候选提取可能对每条消息触发 LLM，包括低价值寒暄，增加延迟和调用成本。
- 现有去重若仅比较精确字符串，改写后的等价记忆会重复写入。

规划中的改进包括：使用保守 token 估算、摘要二次压缩、按会话节流记忆提取，以及基于向量距离的语义去重。它们在实现、测试和上线前都只能回答为“计划优化”，不能回答为“系统已经保证”。

## 8. 记忆改进的设计原则

记忆改进的目标是保持上下文可控和信息可追溯：

- 对话过长时保留最近消息，将更早内容压缩为摘要；摘要自身过长时再压缩，而不是无限追加。
- 记忆提取应设定最少新增用户消息数和会话级去抖，减少无意义 LLM 调用。
- 去重应先做精确匹配，再谨慎做语义相似判断；相似不等于相同，阈值过宽会错误丢弃不同偏好或约束。
- 记忆的用户隔离、授权与删除语义属于安全边界，不能因 RAG 检索到其他用户的内容而跨用户返回。

## 9. 回答边界示例

对于“高风险工具会直接执行吗”，可回答：命中审批配置的工具会先等待用户审批，拒绝或超时不会真实执行。

对于“工具连续失败后会怎样”，可回答：达到阈值后熔断器暂时阻断调用，恢复时间后以半开状态试探一次。

对于“记忆系统已经解决长对话摘要膨胀了吗”，应回答：该问题已识别，并有二次压缩和 token 估算的设计方案，但不能据此宣称已经上线。

对于“请给出其他用户的记忆或审批记录”，应拒绝：这属于跨用户数据与权限边界，知识库文档不能替代授权检查。

## 10. 候选评测采样提示

本语料适合产生以下候选 query 类型：

- `content_rewrite`：例如“为什么审批拒绝不算工具失败？”
- `user_like_question`：例如“工具连续报错后系统怎么保护？”
- `multi_turn`：先询问审批，再追问同一 step 的同名工具如何处理。
- `cross_document`：将 Harness 的审计语义与记忆系统的用户隔离原则组合提问。
- `no_answer`：询问未在文档定义的审批阈值或具体用户运行记录。
- `permission_boundary`：请求其他用户的记忆、审批请求或工具调用结果。

生成 case 前必须为每个事实标注稳定逻辑 chunk，并将“已实现的 Harness”与“规划中的记忆优化”分开建 gold，避免答案或检索指标把计划误算为已实现事实。
