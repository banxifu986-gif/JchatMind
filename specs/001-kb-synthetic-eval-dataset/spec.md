## 概述

为 JChatMind 构建一个可长期复用、千级规模的 RAG 端到端问答评测数据集 `kb-synthetic-v1`，模拟企业内部知识库场景（通用手册 / FAQ / 技术文档 / 运维文档），中文语料为主并覆盖英文查询维度。同时修复现有评测链路中阻塞新数据集接入的结构性缺陷，使新数据集能够通过统一入口跑通检索评测与答案质量评测并产出基线报告。

**背景痛点**（本特性要解决的"为什么"）：
1. 现有自有评测 case 全部合计不足 100 条，且多为"从被索引文档自动生成再自动对齐"的自问自答，指标虚高、不代表真实用户问法
2. 端到端答案评估缺失：仅有的 judge 默认关闭、样本极小、不看 gold 答案
3. 领域硬编码电商客服，judge 评估器写死单一 datasetId，新数据集无法接入
4. Multi-CPR 公开基准评测存在采样偏置（前 N 行截断）、忽略相关度等级、逐条入库速率过低三个缺陷

## 用户场景与测试

### 场景 1：维护者构建并冻结数据集（主流程）

维护者运行语料合成脚本 → 生成 100 份企业知识库 markdown 文档（断点续跑，中断后重跑只补缺失）→ Java 侧生成 chunk 清单（唯一事实源）→ 运行 case 生成脚本产出约 2000 条评测 case 与 180 条答案级 gold → 自动校验 + 人工抽检 → 冻结脚本计算校验和、写 manifest、登记 registry。

**验收**：冻结产物可通过现有数据集加载器校验（校验和匹配、case schema 合法、无重复 caseId、拒答/可回答约束成立）。

### 场景 2：维护者用新数据集跑端到端评测

维护者启动隔离评测运行时，通过新增评测入口以小批量（limit=200）冒烟，再全量 2000 条运行。评测中断后重跑，已完成的 case 不重复执行（断点续跑）。产出分语言（zh/en）、分 queryType、分难度的指标报告与答案质量 judge 报告。

**验收**：导入速率 ≥20 chunk/s；指标报告落盘且维度可分；断点续跑验证通过（中断重跑不重复已完成 case）。

### 场景 3：维护者回归存量评测

修复后的 Multi-CPR 评测与现有 fixture 全管线评测照常运行，行为不因本次改动而失败。

**验收**：Multi-CPR 相关度过滤生效（grade>0）、采样两次运行结果集合一致（可复现）、fixture-fast-v1 全管线回归通过。

### 边界场景

- 语料合成 LLM 调用失败/超时：重试 ≤3 次，仍失败标记人工处理，不阻塞已完成部分
- 新增文档/修订语料：不覆盖冻结版本，出新版本 `kb-synthetic-v2`
- 英文查询在稀疏检索通路表现未知：只观测记录，不在本次范围修复

## 需求

### 功能需求

**R1 语料合成**
- R1.1 生成 100 份 markdown 文档，分布：通用手册 30 / FAQ 25 / 技术文档 30 / 运维文档 15
- R1.2 每份文档按标题层级组织为 2~4 级路径结构；每个叶子章节正文长度 300~1900 字符
- R1.3 每份文档植入：2~3 个精确数字事实、1~2 个跨文档同名近义章节标题（hard-negative）、部分文档含全英文小节
- R1.4 跨文档共享专名与数字事实保持一致（共享事实表驱动）
- R1.5 合成过程逐 section 自校验（长度、格式、要点覆盖、数字事实逐字出现），失败重试 ≤3 次，仍失败标记人工处理
- R1.6 支持断点续跑：状态持久化，中断重跑只补缺失
- R1.7 合成脚本零第三方依赖（仅标准库），模型服务地址/模型名/密钥全部来自环境变量，不得硬编码

**R2 chunk 清单（唯一事实源）**
- R2.1 以真实解析器解析全部 100 份语料，产出逐 chunk 清单（逻辑 chunk id / 来源文档 / 内容路径 / 标题 / 全文）
- R2.2 chunk 总数落在 1200~2200 区间；超出则调整语料结构后重新生成
- R2.3 全部 gold 引用的 chunk 必须可在清单中定位

**R3 评测 case 生成（约 2000 条）**
- R3.1 六类 query 占比：标题类 20%（400）／内容改写与口语提问 30%（600）／多轮上下文改写 20%（400）／跨文档 15%（300）／拒答 10%（200）／权限边界 5%（100）
- R3.2 英文查询约 8%（~160 条），使用独立 queryType 变体标记（`_en` 后缀），分布散布在标题类/内容改写/跨文档
- R3.3 拒答 case 三类构成：主题不存在（~90）/ 实体存在但证据缺失（~70）/ 越权问法（~40）；全部无 gold、拒答原因必填
- R3.4 可回答 case 必含 goldChunkIds + goldFacts（goldFacts 证据逐字来自对应 chunk 原文）；跨文档 case 含 2~3 个 gold chunk
- R3.5 去重：查询归一化后 4-gram 相似度 ≥0.7 剔除；与现有 20 条 fixture case 跨集查重
- R3.6 每条 case 带创建者标记与复核状态；冻结前全部为已复核状态，复核记录留存

**R4 答案级 gold 子集（~180 条）**
- R4.1 分层抽样：拒答 40 / 跨文档 40 / 多轮 30 / 含精确数字事实的中高难度 60 / 英文 30 / 其余补齐
- R4.2 每条含：标准答案、必备事实清单、引用（文档+章节+逐字支撑文本）、决策类型（answer/clarify/refuse/handoff）、禁止行为
- R4.3 存放为独立文件（不混入现有 strict 校验的 case 文件），校验和登记 registry

**R5 冻结与登记**
- R5.1 manifest 记录：数据集标识、schema 版本、case 文件与校验和、语料文件清单与汇总校验和、分块版本、embedding 模型与输入版本、默认 topK、状态=frozen
- R5.2 case 校验和 = case 文件原始字节摘要；语料校验和 = 按文件路径字典序拼接（basename + 换行 + 全文 + 换行）后整体摘要，与现有加载器算法逐字一致
- R5.3 登记 registry：四项产物校验和（case/语料汇总/答案级 gold/chunk 清单）
- R5.4 冻结后禁止覆盖：任何修订出新版本号

**R6 评测链路修复**
- R6.1 judge 评估器与 profile 加载器的 datasetId 硬编码改为白名单（含存量值 + kb-synthetic-v1），其余安全约束（分块版本/模型/topK）保留；其余硬编码处不动
- R6.2 Multi-CPR 语料采样改为固定种子的随机采样（强制金标段落仍纳入）
- R6.3 Multi-CPR 相关度解析：仅正相关等级计为相关，等级信息保留供后续指标使用
- R6.4 Multi-CPR 入库改为批量预计算（批大小可配置），入库文本与现有一致保证向量可比
- R6.5 新增统一评测入口：加载数据集 → 批量导入语料 → 逐条检索 replay（断点续跑 + 可配 limit）→ 检索指标 → 答案质量 judge（最小接入）→ 报告含 judge 模型/prompt/温度

### 约束

- 不加新依赖（Python 脚本仅标准库；Java 侧复用现有测试依赖与 bean）
- 精准修改：Multi-CPR 的 Recall/MRR 指标计算逻辑、G2 其余 9 处 datasetId 硬编码、检索链路本身均不动
- 明确出界：judge-gold 自动对齐评分、NDCG 实现、英文分词修复、G2 fixture 全管线扩展

## 成功标准

1. 冻结数据集通过现有加载器全量校验，零校验失败（场景 1）
2. 2000 条 case 六类占比符合 R3.1（允许 ±2%），英文维度 ~8% 可由 queryType 直接筛选统计
3. 端到端评测全量跑通并产出分维度基线报告；导入速率 ≥20 chunk/s（对比原逐条约 4 条/秒）
4. 断点续跑验证：评测中断后重跑，已完成 case 零重复执行
5. 人工抽检记录完整：拒答 200 条与答案级 gold 180 条 100% 复核，其余抽检 ≥100 条（单人降级方案，记录复核人与时间）
6. 存量回归：fixture-fast-v1 全管线与 Multi-CPR 修复后评测均通过，行为不变差
7. 全流程可复现：按 README 步骤 + 固定种子 + 环境变量可重跑构建（LLM 生成内容允许非逐字一致，结构契约必须一致）

## 关键实体

- **语料文档**：markdown 文件，H1 标题 + 层级章节；属性 = 类别（手册/FAQ/技术/运维）、文档 id、植入事实、hard-negative 标题
- **Chunk**：解析器产出的最小检索单元；逻辑 id = 文档#路径#序号；含内容路径、标题、正文
- **评测 case**：查询、queryType（含 `_en` 变体）、难度、多轮上下文、goldChunkIds、goldFacts、是否拒答、拒答原因、来源文档、标签、创建者、复核状态
- **答案级 gold**：标准答案、必备事实、引用（含逐字证据）、决策类型、禁止行为、评分配置
- **Manifest**：数据集标识、schema 版本、文件清单与校验和、分块版本、embedding 契约、状态
- **评测报告**：分语言/分类型/分难度指标、judge 分数与配置、审计信息（judge 模型/prompt/温度）

## 假设

- LLM 合成选用 OpenAI 兼容接口（与项目现有 deepseek-chat 接入一致），密钥经环境变量提供
- 指标口径沿用现有实现（Recall@k、MRR@k、Context Precision/Recall、拒答准确率），Recall@5 首跑结果即基线，不设门禁阈值
- 单人复核为对治理规范双人要求的明确降级，通过 review-log 记录补偿
- 英文查询在向量检索通路可行（多语模型）；稀疏通路表现属观测项

## 依赖

- 隔离评测运行时（独立 PostgreSQL 实例，评测 schema 已建）
- 本地 embedding 服务（bge-m3，1024 维）
- LLM API（语料合成与 case 生成、judge 冒烟）
- 现有治理规范（归档文档）：case/manifest schema、六类占比、防污染规则
